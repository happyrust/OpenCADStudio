# P&ID 界面大改：设计稿与现有实现的对照表

这份文档把设计稿 `docs/pid-platform/design/pid-platform.pen` 里的外壳和 14 个界面逐个对到仓库里现有的实现，说明界面上每一类数据和操作现在有没有真实来源、缺什么后端、建议怎么做。它用来定两件事：外壳上每个元素做不做，以及编辑器、调色板、属性面板之外的 11 个界面各做到什么范围。

## 0. 依据与口径

- **代码基准**：worktree `ocs-pid-collab`，分支 `pid-collab-ui-20261111`，提交 `1fd890278`，读的时候工作区没有未提交的改动。只读了代码，没有构建，没有运行程序；凡是靠读代码推断行为的地方，文中写了「按代码推断」。
- **设计稿**：`.pen` 文件版本 2.21，顶层 15 个节点：外壳组件 `p0zWw`（`component/App Shell`）加 14 个引用它的界面实例。每个界面的内容在实例的 `descendants.tqvXC`（外壳的 Content 槽）里。区域、表头、按钮、字段的文字都是用脚本从文件里抽出来的，对照表建在这些文字上。设计稿只有一套（暗色）变量，共 24 个；亮色主题和协同界面的画框不在已提交的这一份里。
- **设计稿里的数字全是演示数据**（128 张图纸、186 个符号、312 个类型……）。现在程序里真实的数量是：符号 7 个分 3 类（`assets/pid-symbols.json`），类型 4 个（`assets/pid-types.json`），生效的位号规则 5 条（设备的一条在类型库里，阀门、仪表、管线、管路四条在 `default_tag_rule` 里），角色 5 个，图纸状态 3 个。界面接上真实来源之后显示的就是这些数。
- **「有 / 部分 / 无」的含义**
  - 有：能指到具体的函数或命令，并且它在产品路径上被调用。
  - 部分：有数据或纯函数但没有接到命令或界面；或者只覆盖设计稿画的一部分。
  - 无：在 `src`、`crates`、`assets`、`tests`、`examples` 的 1306 个源文件里检索不到实现。
- **工作量级别**
  - 小：只动界面层，数据和命令已经在。
  - 中：界面之外要在已有模型上加查询或小命令，不动持久化格式和协同协议。
  - 大：要新的数据模型、持久化或服务器接口，或者同时动客户端与服务器。
- `gap-analysis.md` 与 `requirements/95-reuse-mapping.md` 写在前几轮开发之前。它们说「不存在」的位号主数据、拓扑持久化、协同、权限、审计，现在都有实现；它们说可以复用的识别器、导出等没有变。本文一律以代码为准。

### 0.1 现有的 P&ID 实现（后文反复引用）

| 能力 | 在哪里 |
|---|---|
| 每个对象的 P&ID 语义：九个键写在 `PID_AUTHOR` XDATA 里 | `src/pid/persist.rs`（`PidAuthor::store` / `load`） |
| 图级数据：模型空间扩展字典下的 XRecord | `src/pid/graph_data.rs`（`store` / `load`，四个 key；实际写入的只有拓扑表） |
| 类型库模型（类型树、属性分组、数据要素、沿树继承的位号规则与颜色） | `src/pid/type_lib.rs`（`TypeLib`） |
| 位号规则与引擎（生成、查重、状态、批量序号） | `src/pid/tag_rule.rs`、`src/pid/tag_engine.rs`（`generate`、`TagSequencer`、`refresh_statuses`） |
| 符号库（分类、符号图形、端口、符号↔类型映射） | `src/pid/symbols.rs`（`SymbolLibrary`） |
| 拓扑表（管线、管路、管段、管件、连接符） | `src/pid/topology.rs`（`TopologyTable`） |
| 属性下传（管线→管路→管段）与保存前门禁 | `src/pid/propagate.rs`（`propagate_line_to_runs`、`gate_save`） |

| 四个停靠面板：符号调色板、图例识别清单、备份浏览器、协同面板 | `src/ui/window/pid_palette.rs`、`pid_legend_list.rs`、`pid_backup_browser.rs`、`pid_collab.rs` |

| 协同客户端（WebSocket、状态、认领、变更收发、只读把关） | `src/app/collab/` |
| 协同服务器（会话、占用、三级权限判定、冲突与裁决、只追加审计） | `crates/ocs_collab`、`crates/ocs_collab_server` |

有三件事对界面范围影响最大，先说在前面：

1. **类型库只有内置的一份，而且没有编辑入口。** 程序里取类型库的地方全是 `TypeLib::embedded()`（`pidpalette.rs`、`pidpipe.rs`、`pidbulk.rs`）。`TypeLib::store` / `load` 只在测试里被调用，`TypeLib` 也没有增、删、改类型的方法。
2. **协同服务器的数据只能读到很少一部分。** 它的 HTTP 接口只有 `/health`、`/session`、`/audit`、`/permission/check`、`/drawing/{id}/state`、`/drawing/{id}/objects`、`/drawing/{id}/topology`、`/conflicts`、`/conflicts/{id}/resolve`（`crates/ocs_collab_server/src/http.rs` 的 `router`）。没有列出图纸、用户、角色、PBS 节点的接口，也没有改 ACL 的接口；用户、PBS、ACL、图纸只能在启动时用 `--seed` 文件灌入（`store.rs` 的 `SeedDoc`）。桌面端到现在只用 WebSocket：在 `src` 里检索不到调用这些 HTTP 接口的代码。
3. **现有功能的入口大多是命令行。** 功能区里的 P&ID 组只有图例清单、找位号、组合、解组、出 PDF 五个按钮（`src/modules/draw/pid.rs`）。放符号、画管线、插管件、连接符、设属性、协同配置，都要在命令行里敲。设计稿的外壳里没有命令行，这件事要定（问题 2）。

### 2.2 导航（`U8XVq7`）

四组 14 项：设计（工作台、图纸管理、P&ID 编辑器、符号调色板、属性面板）、配置（业务类型库、标准图例定制、符号编辑器、位号规则、颜色规则、主数据管理）、校验交付（设计规则检查、材料清单）、平台（权限管理）。选中项用 `accent-soft` 底色。

- 导航本身是界面状态，没有数据问题。每一项出不出现，取决于那个界面做不做。**建议没有实现的界面不出现在导航里**，而不是置灰留着：置灰的入口点进去是空的，正是这次要避免的。
- 「符号调色板」「属性面板」在导航里是独立的两项，但它们的面包屑写的是「P&ID 编辑器 / 符号调色板」「P&ID 编辑器 / 属性面板」，而且编辑器界面自己已经带了一条小调色板和一块 Inspector。这两项是独立的整页，还是编辑器里两块面板的展开状态，要定（问题 2）。

**同步状态（`khu5r`）**：设计稿画一个绿点加「数据中心已同步」。现状是**部分**：连接状态是真的（`State.connected`、`reconnect_attempts`、`last_error`、`diverged`、`readonly`、`base_revision`，协同面板里已经有状态点 `pid_collab::status_dot`）；「数据中心」没有对应物——服务器不存图纸，只存语义操作和审计。建议：做，文字按真实状态写，一共六种：未配置、连接中（第 n 次）、已连接（修订 N）、已断开并重试、与房间不一致、只读。这一项属于 CT-16。

## 4. 建议的实现次序

**第一批：外壳与三个编辑器界面（CT-6 到 CT-11）。** 要接的功能都在，是「改接」。次序上先外壳骨架和「命令提示放哪儿」的决定，再编辑器，再调色板与属性面板。其中带的小补：信号线线型、放仪表时问仪表功能、自动保存时刻、放置合一、实例列表的纯函数。

**第二批：其余 11 个界面里现在就能接上真实数据的（只读或局部）。**

| 界面 | 能如实做到的范围 | 级别 |
|---|---|---|
| 9 位号规则 | 规则列表、字段、对当前图算出的下一个与后续位号、沿类型树的继承来源 | 小到中 |
| 6 业务类型库 | 类型树、标识、分组、要素的只读浏览 | 小 |
| 7 标准图例定制 | 标准名、分类、符号网格、符号属性、类型↔符号映射的只读浏览 | 小 |
| 1 工作台 | 本机最近文件、快捷入口；连上服务器时的最近动态（读审计） | 中 |

**第三批：要先补后端的。**

| 界面 | 先补什么 |
|---|---|
| 2 图纸管理 | 服务器的 PBS 与图纸列表接口（最小档）；登记与状态切换（中间档）；版本与文件存储（完整档） |
| 14 权限管理 | 服务器的用户、PBS、ACL 只读接口（只读档）；写接口（可管理档） |
| 6、7、9 的可编辑版本 | 类型库与符号库的修改操作、保存与加载路径、归属的决定 |
| 1 工作台的指标条 | 图纸列表接口；待处理问题依赖界面 12；已发布依赖发布功能 |

第二、三批共用一层基础：桌面端调协同服务器 HTTP 接口的客户端（现在没有）。建议作为单独的一项先做。

**第四批：几乎全新的功能。**

| 界面 | 最小的真实版本 | 完整版本 |
|---|---|---|
| 12 设计规则检查 | 四条写死的检查加违规表与定位（中） | 规则语言、规则包、豁免、触发时机（大） |
| 13 材料清单 | 当前图纸的聚合加导出（中） | 跨图纸、报表模板（大） |
| 11 主数据管理 | 四张简单取值表，属性输入框取候选值（中） | 引用、同步更新、停用（大） |
| 10 颜色规则 | 按类型着色，没有条件表达式（中） | 条件表达式规则（大） |
| 8 符号编辑器 | 没有合适的最小版本 | 符号写回库、端口与标记字段（大） |

这五个里，12 的最小版本与编辑器的关系最直接（工具栏按钮、违规标记），13 的最小版本最独立。

## 5. 要操作员定的问题

**问题 1：其余 11 个界面这一次做到哪一档。**
现状：11 个界面里，没有一个能照设计稿完整接上真实数据；4 个能做只读或局部，2 个要先补服务器接口，5 个是全新的功能。
- 甲：只做第二批（4 个界面的只读或局部版本）。导航里出现 3 + 4 = 7 项，其余 7 项不出现。工作量：4 个小到中的任务。界面上少的是：图纸管理、权限、规则检查、材料清单、主数据、颜色规则、符号编辑器这些入口，以及所有「编辑配置」的能力。
- 乙：甲，再加图纸管理的最小档与权限管理的只读档（各要服务器加只读接口）。导航 9 项。多出大约 5 个任务，其中服务器 2 个。
- 丙：乙，再加规则检查、材料清单的最小版本。导航 11 项。再多大约 4 个任务。
- 丁：全部照设计稿做完。要新做类型库与符号库的编辑和保存、主数据、规则引擎、图纸版本、自定义角色等，规模与前几轮整个 mission 相当。
建议乙或丙。

**问题 2：没有命令行的外壳里，命令的提示和报错放哪儿；调色板与属性面板是整页还是面板。**
现状：现有功能靠命令行给提示、列选项、报错；设计稿的外壳没有命令行。设计稿把「符号调色板」「属性面板」画成导航里独立的整页，同时编辑器里又有小调色板和 Inspector。
- 提示：甲，编辑器底部保留一条可收起的命令行（改动最小，设计稿上没有这一条）；乙，提示与报错改到状态栏和画布上的浮条里，命令行不再可见（每个命令的提示与选项都要改成按钮或浮条，工作量大得多，而且脚本与自动化仍然需要命令通道）。建议甲。
- 两个界面：甲，按设计稿做成两个整页，调色板页右侧就是真实画布，属性页是对象管理器；乙，只做编辑器里的两块面板，导航里不出现这两项。建议甲，但调色板页与编辑器共用同一个画布，而不是两个画布。

**问题 3：「项目」是什么。**
现状：仓库里没有项目实体，标题栏的项目选择和工作台的项目信息没有来源。
- 甲：这一次不引入项目，标题栏那个位置显示协同服务器地址。少的是：切换项目、项目名。
- 乙：把服务器的 PBS 根节点当作项目（只读显示根节点名，不能切换）。小，但要服务器的 PBS 只读接口。
- 丙：服务器加项目表、图纸归属项目、会话带项目。大，协议与表结构都动。
建议甲或乙。

**问题 4：类型库、位号规则、符号库、主数据归谁——随图还是随项目。**
现状：类型库和符号库是程序内置的，只读；架构上给类型库和位号规则在图里留了 XRecord 的位置，但没接上。两个人协同时现在用的是同一份内置库，所以不会不一致。
- 甲：随图（存进图的 XRecord）。实现路径已经有一半（`TypeLib::store` / `load`），但每张图各有一份，改了一张图的规则不影响别的图，协同双方的库也可能不同。
- 乙：随项目（服务器上一份，或项目目录里的文件）。要新的存取路径，但规则只有一处。
- 丙：这一次保持内置只读，不做编辑。界面 6、7、9 只做只读，8、11 不做。
这个问题决定界面 6、7、8、9、11 的可编辑版本能不能开工。建议这一次选丙，把甲或乙留到下一轮。

**问题 5：图纸状态与角色，照设计稿还是照代码。**
现状：代码里图纸状态是三个协同状态（单人编辑、协同编辑、只读），角色是固定的五个；设计稿画的是五个生命周期状态（设计中、校审中、已审核、已发布、已冻结）和可自定义的角色（工艺设计、仪表设计、校审、外协只读）。
- 甲：界面照代码显示真实的三个状态和五个角色。不用改后端；与设计稿的文字不同。
- 乙：实现生命周期状态的流转与自定义角色。大：判定链、表结构、协议、已有的 32 条权限断言都受影响。
建议甲。

**问题 6：仪表回路。**
现状：没有回路的任何模型。编辑器工具栏的「仪表回路」、画布上的回路框、Inspector 的「所在回路」、规则「仪表须归属回路」都依赖它。
- 甲：这一次不做，这几处不画。
- 乙：做回路（新的分组模型、持久化、位号规则里的回路序号、协同里的新操作种类）。大。
建议甲。

**问题 7：调色板要不要真正的拖放。**
现状：现在是单击格子后在画布上点位置；从面板拖到画布的机制没有，本地的 iced 分支按约定不改，可行性没有验证。
- 甲：保持「单击后放置」，把设计稿的落点规则（落在管段上就插入并断开，落在空白处就独立放置）做进放置里。中，风险低。界面上的说明文字相应改掉。
- 乙：做拖放。先要一次可行性验证；可能受 iced 的限制。
建议甲。

**问题 8：符号与类型的内容要不要扩充。**
现状：内置符号 7 个分 3 类，类型 4 个。设计稿的调色板画了阀门 14、管件 6、阀门附件 4。界面接上真实数据后，调色板只有 7 个格子。
- 甲：先不扩充，界面如实显示 7 个。
- 乙：加一项内容任务，按一个选定的标准补符号（每个符号要图形、端口、类型映射）和对应的类型。工作量随数量走，补到设计稿那个规模大约是几十个符号。补之前要先定用哪个标准。
这件事不影响界面能不能做，影响的是做出来像不像一个能用的工具。

**问题 9：全局搜索与通知。**
现状：都没有后端。
- 甲：都不画。
- 乙：搜索做成「当前图纸的位号、符号库、类型库」范围内的查找，通知做成协同事件（待裁决冲突、认领被拒、只读、不一致）的角标。各是一个小到中的任务，文字要与范围一致。
建议先甲，协同界面（CT-16、18）落地后再看通知要不要并进去。

## 6. 没有核实的地方

- 全部结论来自读代码与检索，没有构建，没有运行程序。
- `PIDTAG <位号>` 对 `PIDINSERT` 放的符号能不能定位：按代码推断不能（它读的是识别结果，识别器里没有 `PID_SYM`、`PID_AUTHOR`），没运行验证。
- 放下的仪表位号为空：按 `write_pid_author` 与 `tag_engine::render` 推断，没运行验证。
- 信号线与工艺管线画法是否有区别：`pidpipe.rs` 里没看到设线型，没看图层与实际显示。
- 多选时特性面板是否显示「P&ID 属性」组：只找到单选路径上的一处调用。
- 连接符旁是否在图面上写出对端图号。
- `HELP` 的在线 wiki 上有没有 P&ID 命令的页面。
- iced 里做面板到画布的拖放是否可行。
- 自动化通道的 `records` 能否按 XDATA 里的 P&ID 属性过滤。
- 设计稿只读了已提交的这一份；亮色主题与协同界面的新画框不在范围内。原型（`docs/pid-platform/prototype/`）与 `test-surface.md` 只看了目录，没有逐项与设计稿对照。
- 文中的工作量级别是按「要动哪几层」估的，没有按人天估。
