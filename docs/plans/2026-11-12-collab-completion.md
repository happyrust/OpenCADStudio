## 0. 三项共用的约定

- **线上的名字**。对象仍按位号称呼（`architecture.md` §3.2）。没有位号的东西（管段、打断符、不单独编号的管件、连接符）在线上按「它属于谁、在哪里」称呼：所属管路或管线的位号，加坐标。句柄只是同一份文件的两个客户端之间的提示，新建出来的实体在两边的句柄本来就不同，所以这三项里**没有任何一处靠句柄认对象**。
- **坐标**一律是世界坐标的 `[x, y]` 数组，与 §3.2 的 `points`、`at` 同形。两点「相同」的判据是各分量相差不超过 `1e-6`。
- **`object_ref` 由服务器在广播时改写**：拓扑类操作（`add_pipe_run`、`insert_fitting`、`update_pipe_run`、`create_connector`）广播出来的 `object_ref` 是所属**管线**的位号（服务器按管线判拓扑的先后，审计也记在管线名下）。客户端读这几类变更时不看 `object_ref`，只看 `tag` / `run_tag` / `line_tag`。
- **一步一个 op** 不变：一个撤销步里的全部变更装在一个 `op` 里（第一条是载荷本身，其余在 `changes` 下）。
- **旧客户端**读到不认识的 `kind` 会照现有规则把自己标成「与房间不一致」并停止提交（`changes_this_client_cannot_read_are_named_not_dropped`）；**旧服务器**把不认识的 `kind` 当不透明操作整体提交、原样广播。两头的新字段都带 `#[serde(default)]`，缺了按没有处理。协议没有版本号字段，这次也不加：每一处新增都能被旧的一方安全地略过或拒收。
- **服务器的持久化**：`ops` 表存的是广播出去的 `changes` 原文，服务器重启时逐条重放进内存里的图面模型。这三项都不改表结构；新种类的变更随原文进表，重放时由同一段代码读。旧库照常能读（旧库里没有新种类）。

## 1. CT-13 管线、管路、管件的新建与删除进入协同

### 1.1 现状

- 本地：`PIDPIPE` 画管线（每一段一条 `Line`，都带管线位号）、`PIDPIPE run` 画管路（一个带管路位号的 `Point` 作本体，每一段一条不带位号的 `Line` 作管段）、`PIDFITTING` / `PIDBREAK` 在管段上插管件或打断符（原管段缩短，另建第二段，管件是一个 `Insert` 或一条 `Line`），关系记在图级 XRecord `PID_AUTHOR_TOPOLOGY` 里，以句柄为外键。删除没有钩子：实体删掉以后，表里的记录等到下一次新建前的 `prune` 才清。
- 协同：`broadcast::changes_of` 对「有位号、独立的符号」说 `insert_symbol` / `delete_object`，对已有对象说 `set_tag` / `set_property`；管线、管路、管段、管件的新建和删除什么都不说。对端没有这条管线，之后对它的属性修改到了对端「对不上对象」，对端被标成不一致。
- 服务器：`ocs_collab::conflict` 认 `create_pipe_line`、`add_pipe_run`、`insert_fitting`、`create_connector`、`delete_object`，后面三个拓扑类按「同一条管线的连接关系」判先后（落后的回 `STALE_BASE_REVISION`，并列窗口内的两条成冲突条目）。

### 1.2 做法：管线按「有这些段」说，管路按「现在是这个样子」说

管路的零件（管段、管件）没有位号，而且一步操作会同时新建、缩短、删除其中几个（插阀门是「缩短一段、新建一段、新建一个管件」，撤销它是反过来，单删阀门又是另一种结果）。逐个动作去说，对端就得照着重演每一种动作，撤销、重做、单删零件各要一套，漏一种两边就悄悄不一样。

所以管路不说动作，说**结果**：凡是动了某条管路零件的一步，都带上这条管路此刻完整的零件清单（`run`），对端把自己图里这条管路的零件**对齐到这份清单**——坐标对得上的留着，对不上的删掉，缺的补上，然后重写拓扑表里这条管路的记录。对齐是幂等的：同一份清单应用两次，第二次什么都不改。新建、插管件、打断、删零件、撤销、重做、裁决后的重放，走的是同一段代码。

三个既有的种类名照用（服务器和契约都认它们），它们标明「这一步是什么」，清单说明「做完是什么样」：

| 这一步做了什么 | 说成 |
|---|---|
| 新出现了一条管线或信号线的若干段 | `create_pipe_line`（带这些段） |
| 新出现了一条管路的本体 | `add_pipe_run`（带 `run` 清单） |
| 某条已有管路上新出现了管件（含打断符） | `insert_fitting`（带 `run` 清单） |
| 某条已有管路的零件有别的变化（删了管段或管件、撤销了插入、端点动了） | `update_pipe_run`（**新种类**，带 `run` 清单） |
| 某条管路的本体没了 | `delete_object`，`object_ref` 是管路位号 |
| 某条管线、信号线一段都不剩 | `delete_object`，`object_ref` 是线的位号 |
| 有独立位号的管件（阀门）没了 | `delete_object`，`object_ref` 是阀门位号，后面跟着所在管路的 `update_pipe_run` |

判定「这一步动了哪些管路」只看撤销步里的实体镜像（哪些带 `topology` 的实体新建了、删了、几何变了），清单从这一步做完后的图里读。所以它仍然挂在 `push_undo_entry` 这一个汇聚点上，撤销与重做也各在做完之后照同样的办法说。

### 1.3 消息与字段

```json
{ "kind": "create_pipe_line", "tag": "L-1001", "type": "PIPE_LINE",
  "points": [[0,0],[200,0]], "pieces": [[0,0,200,0]],
  "props": {}, "tag_source": "auto" }
```

- `type`：`PIPE_LINE` 或 `SIGNAL_LINE`（信号线也走这一条；没有 `type` 按管线）。
- `pieces`：每一段的 `[x1, y1, x2, y2]`，是客户端认的；各段首尾相接时另带 `points`（§3.2 的写法，脚本客户端可以只给 `points`）。
- `props`：这些段带的属性（新画的管线是空的；撤销一次删除把线带回来时是它当时的值）。
- 含义是「这条线**有**这些段」：对端已有同样端点的段就不再建，线原来不存在就连同拓扑表里的 `pipe_lines` 记录一起建。两个人同时各画一条算出同一个位号的管线，两边最后都是「一条线、两处的段都在」——位号就是身份，不改派。

```json
{ "kind": "add_pipe_run", "line_tag": "L-1001", "tag": "L-1001-01",
  "points": [[0,0],[200,0]],
  "run": { "start": [0,0], "props": {"管线号":"L-1001"}, "overrides": [],
           "segments": [ {"start":[0,0],"end":[200,0]} ],
           "fittings": [] } }

{ "kind": "insert_fitting", "line_tag": "L-1001", "run_tag": "L-1001-01",
  "fitting_type": "gate_valve", "at": [100,0], "tag": "V-1001",
  "run": { "start": [0,0], "props": {...}, "overrides": [],
           "segments": [ {"start":[0,0],"end":[84,0],"end_peer":"0:连接点1"},
                         {"start":[116,0],"end":[200,0],"start_peer":"0:连接点2"} ],
           "fittings": [ {"fitting_type":"gate_valve","type":"VALVE","tag":"V-1001","at":[100,0],
                          "block":"PID_SYM_valve_gate_valve","scale":1.0,"rotation":0.0,
                          "props":{}, "tag_source":"auto",
                          "ports":{"连接点1":0,"连接点2":1}} ] } }

{ "kind": "update_pipe_run", "line_tag": "L-1001", "run_tag": "L-1001-01", "run": { ... } }
```

`run` 清单：

- `start`：管路本体（那个 `Point`）的位置；`props` / `overrides`：本体带的属性与覆盖标记。本体是对端新建时照这两项写（不在对端重新继承一遍，这样两边逐字相同）；本体已在时不动它的属性——属性的变化仍然由 `set_property` 说。
- `segments`：按拓扑表里 `pipe_runs[].segments` 的次序。`start_peer` / `end_peer` 是 `"<管件在 fittings 里的序号>:<端口名>"`，没接就不写。
- `fittings`：`fitting_type` 是符号 id 或 `break`；`type` 是 `VALVE`（有独立位号）或 `FITTING`；`tag` 只有阀门写；`at` 是插入点（打断符是标记线的中点）；符号类带 `block`、`scale`、`rotation`、`props`、`tag_source`，打断符带标记线的两个端点 `mark`；`ports` 是「端口名 → 所接管段在 `segments` 里的序号」，没接是 `null`。
- 管段的属性不在清单里：管段始终取管路当前值（`architecture.md` §6.2），对端新建管段时照自己图里这条管路的现值写。

对端对齐一条管路的次序：找管线（没有就是「对不上对象」，照现有规则标不一致）→ 本体没有就建 → 管段按端点配对（两端都对得上的留；只有起点对得上的改终点、**保留句柄**，对应「原管段作第一段」；其余缺的建、多的删）→ 管件按位置配对（缺的建、多的删；本机符号库里没有这个符号就是「对不上」）→ 重写拓扑表里这条管路的 `pipe_segments`、`fittings` 记录与 `pipe_runs[].segments`，`next_run_ordinal` 取不小于这条管路序号加一。

`add_pipe_run` 没带 `run`（脚本客户端照 §3.2 的原样发）时，清单由 `points` 得出：每相邻两点一段，没有管件。`insert_fitting`、`update_pipe_run` 没带 `run` 的，桌面客户端读不了，照「不认识的变更」处理。

`delete_object`：

- 管线位号：删掉带这个位号的全部线段（现有的解析规则已经把「几条带同一位号的线段」当一个对象）。
- 管路位号：删掉本体，**连同以它为宿主的管段与管件**。发送方只在本体确实没了的时候说这一条。
- 阀门位号：删掉那个管件实体；管段不动（本地单删阀门就是留下两段和中间的缺口），紧跟的 `update_pipe_run` 把清单对齐。

**不在这一项里的**（照旧不广播，写进 §1.8）：只删掉一条管线的部分线段、拖动线段或管件（几何修改从来不在协议里，移动符号也一样）、只删本体而留下管段的管路。

### 1.4 次序与幂等

- 一步里的次序：先是现有的逐实体变更（`insert_symbol`、`set_tag`、`set_property`、独立符号的 `delete_object`），再是 `create_pipe_line`、阀门的 `delete_object`、各条管路的说法（按管路位号排序）、线的 `delete_object`。撤销或重做多步时一步一步地说，每一步的清单读的是那一步做完时的图，对端依次应用，中间状态与最终状态都对。
- 服务器按修订号排定全房间的次序，客户端按到达次序应用（修订号不连续即标不一致，现有规则）。
- `create_pipe_line` 是「确保有」，`run` 清单是「对齐到」，`delete_object` 删不存在的对象照现有规则报「对不上」。重连补发（CT-14）按修订号去重，幂等只是第二道保险。
- 自己的 op 回声：照现有规则只推进基线，不再应用。

### 1.5 与认领、只读、冲突规则怎么相处

- **只读**：不变。只读会话的每一步在 `push_undo_entry` 被撤回，服务器在收到 `op` 时先查写权限。
- **认领**：客户端这边照旧看这一步的实体镜像里带的位号（新管路的位号、阀门的位号）。服务器这边补一处：拓扑类操作除了自己的 `tag`，还要看它的 `line_tag` 和 `run_tag`——别人认领着 `L-1001` 时，往 `L-1001` 上加管路、插管件也被 `CLAIM_HELD` 拒绝（改一条被认领的管线的连接关系，同样是那位认领者的事）。
- **冲突**：`update_pipe_run` 与 `add_pipe_run`、`insert_fitting` 一样算「改这条管线的连接关系」：基线落后于别的会话对同一条管线的改动 → `STALE_BASE_REVISION`；并列窗口内两条都按当前修订提交 → 拓扑冲突条目，等裁决。裁决写回的是两条里被选中的那条，原样广播，因为带着清单，落选一方的客户端一对齐就得到选中的结果，不需要另外的回退。
- `create_pipe_line` 与 `delete_object` 的规则不变（新建没有可落后的；删除先查是不是别的管路的端点）。
- 被服务器拒绝的那一步，本地的修改此时还留着——撤回是 CT-14 的事（§2）。

### 1.6 服务器要改的

1. `ocs_collab::conflict`：新种类 `update_pipe_run` 进 `changes_topology()`；`commit_structure` 里，带 `run` 的 `add_pipe_run` / `insert_fitting` / `update_pipe_run` 用清单里的 `fittings`、`segments` **替换**这条管路在模型里的管件与管段（没带 `run` 的 `insert_fitting` 照旧追加一条）；清单里有独立位号的管件登记为对象（这样之后的 `insert_symbol` 查重能看到它，`delete_object` 能删到它）；`delete_object` 一个阀门位号时把它从所在管路的管件里拿掉；`type` 是 `SIGNAL_LINE` 的 `create_pipe_line` 不登记进 `pipe_lines`。
2. `ws::held_by_another`：拓扑类操作多看 `line_tag`、`run_tag` 两个位号。
3. `GET /drawing/{id}/topology` 的 `pipe_runs[]` 多一个 `segments`（清单里的管段），其余不变。
4. 持久化：不改表。`ops` 表里的旧行没有新种类，照常重放。

- 服务器（`ocs_collab` 与 `ocs_collab_server` 的单元测试）：`update_pipe_run` 的先后判定与模型替换、阀门登记为对象、信号线不进 `pipe_lines`、认领着管线时拓扑操作被拒。
- 端到端 `x03_pipe_topology.py`（`VAL-CROSS-003`）：两个真实客户端加服务器。u1 画 `L-1001`（`0,0`→`200,0`）、在它上面画管路、`PIDFITTING gate_valve 100,0`；查服务器广播的 `op_applied`、u2 的拓扑（2 段、阀门两个连接点各接一段的端点、无重叠无缺口）、两侧 `PIDTOPOLOGY` 读回的段数与端点坐标逐个相等、`conflicts` 里没有 `L-1001` 的行；然后 u1 删阀门、删管路、删管线，每一步之后再比两侧。检查读的是两边的图、拓扑表与属性，不是「消息发出去了」。

### 1.8 这一项不做的

- 只删一条管线的部分线段、拖动或拉伸线段与管件：照旧不广播（协议里没有「已有对象的几何」）。两边的图从那时起在几何上不同，不会被标出来。
- 只删管路本体而保留它的管段：对端会连管段一起删。
- 两个人在同一个往返时间内各在**不同管线**上插阀门、本地算出同一个阀门位号：服务器不改派管件的位号（`insert_symbol` 的改派规则没有扩到 `insert_fitting`），两边都会有两个同位号的阀门，位号状态显示重复，要人工改号。
- 审查 N4（`__overrides` 不随变更走）仍然没有修；这一项里只有新建管路本体时带上覆盖标记。

### 1.9 实现记录（与上文不同或上文没写到的）

- **撤销一步之后对端管路的重放。** 本地带结构变化的一步（画管线、管路、插管件都是：它们改拓扑表）在撤销栈里存的是「整个非实体结构」的镜像，撤销时整体换回去。别人在这一步之后建的管路，它们的拓扑表记录不在这份镜像里。所以撤销或重做之后，把这一步之后别人说过的管线再「确保有」一遍、每条管路按**最后一次**清单再对齐一遍；之后被别人删掉的不带回来（`replay_remote_after`）。
- **顺带修掉一个原来就有的隐患**（`keep_structure_ahead_of_peers`）。上面那份结构镜像里还有「下一个句柄从哪里发」、块定义表和已登记的应用名。别人的实体不在任何一步的镜像里，撤销后仍在图里，而句柄的起点退回去了：下一个新建的实体会拿到一个已经有主的句柄，把原来那个实体顶掉；别人放的符号所用的块定义也没了。用例第一次跑就撞上了（对端的一段管段丢了作者记录，符号库被重复定义一遍）。现在撤销 / 重做之后：句柄起点不后退；镜像里没有、而定义实体还在图里的块定义留着；每个块保留它原来列着的实体；登记过的应用名留着。这个隐患对已有的「别人放的符号」同样成立（本地先做一步带结构变化的操作，别人放一个符号，本地再撤销那一步），只是此前没有用例走到。
- **管路的序号（`next_run_ordinal`）是各图自己的计数，不随协同走。** 对端对齐一条新管路时把自己的计数推到不小于它；本地撤销「新建管路」会把计数退回去，对端不退。两边永远不会给两条管路同一个号（对端只会更大，本地再画时用回退后的号，对端照收），但两边「下一条管路叫什么」可以不同。比较两边拓扑的用例与端到端都不比这个数，用例里单独钉了「对端的计数被推过去」和「对端随后新建的管路拿到下一个号」。
- **按位号找对象多一条规则**（`broadcast::resolve`）：没有独立位号的管件显示的是所在管路的位号，于是「带这个位号的实体」不止一个。带同一位号的实体里恰好有一个管路本体、其余都是管件时，这个位号指管路本体。没有这条，对一条带管件的管路改属性，到了对端就是「对不上对象」。
- **单删阀门之后再撤销**：如果两步之间到过别人的管路变更，本地拓扑表在对齐时清过一次悬空记录，撤销把阀门实体带回来时表里已没有它的记录——这时说出去的清单里这个阀门没有端口绑定，两边一致（都没有绑定），但与撤销前不同。没有处理。
- **服务器侧的全有或全无**没有在这一项里动：一步里既有拓扑变更又有字段修改、其中一条被拒时，其余的仍会生效。放在 §2（CT-14）与「被拒的一步撤回」一起定。

## 2. CT-14 离线编辑排队，重连后对账；被拒的修改撤回

### 2.1 现状

- 断线期间：`broadcast_changes` 见 `connected == false` 就什么都不做，修改只在本地。
- 重连：`hello` 不说自己到了哪个修订；`welcome.base_revision` 是房间当前的修订。客户端发现它比自己的大，就把自己标成「与房间不一致」并停止提交——其间的变更没有人补给它。
- 自己的 op 被拒：`error` 帧只有 `code` 和 `message`，说不出是哪一个 op；本地的修改留着，命令行有一句话。
- `SESSION_EXPIRED`：只是一条错误。服务器不让同一条连接重新 `hello`，所以这条连接从此什么都做不了，直到它自己断。
- 一个 op 里的几条变更各判各的：字段修改里有一条让位，其余的照样生效；这对拓扑类也一样——一步里「插管件」被拒而同一步的字段修改生效，是半步。

### 2.2 消息与字段（都是可选字段，缺了按没有处理）

客户端 → 服务器：

```json
{ "type": "hello", "user_id": "u1", "drawing_id": "PID-1101", "mode": "协同编辑",
  "client_version": "…", "since": 6 }
```

- `since`：这张图已经应用到的修订。只有本次运行里在这张图上有过会话的客户端才带；第一次加入不带（照旧：把图当作房间现在的样子）。

服务器 → 客户端：

```json
{ "type": "welcome", "session_id": "…", "base_revision": 9, "peers": [], "claims": [], "replay_from": 6 }
{ "type": "error", "code": "OP_SUPERSEDED", "message": "…", "op_id": "op-s1-12", "rejected": true }
{ "type": "conflict", "conflict_id": "…", "object_ref": "P-1001", "field": "设计压力",
  "value_a": "1.6MPa", "value_b": "2.5MPa", "op_ids": ["op-s1-12", "op-s2-7"] }
```

- `welcome.replay_from`：服务器**会补发**时才有，值等于 `hello.since`。紧跟这条 `welcome`、在这条连接上的任何别的帧之前，服务器把修订 `since+1 … base_revision` 的 `op_applied` 逐条原样重发（来自 `ops` 表，就是当时广播的那一帧）。没有这个字段就是不补发：第一次加入、旧客户端、服务器没有库、`since` 比房间还新（服务器换过库）、或者日志不连续。
- `error.op_id`：这条错误答的是哪个 op。凡是答 `op` 的错误都带。
- `error.rejected`：`true` 表示这个 op **整个没有生效**，客户端据此把那一步撤回。没有或 `false`：这条错误说的是 op 里的一条变更（落后让位、对象已删），同一个 op 的其余变更照样生效并会有 `op_applied`。
- `conflict.op_ids`：并列的两个 op。它们既不会有 `op_applied` 也不会有 `error`，各自的作者靠这个字段知道「我那个 op 进了冲突条目」。

### 2.3 服务器的规则

1. **补发与加入是一步**：`hello` 在图面锁内同时做三件事——订阅房间、读当前修订、读 `since` 之后的 op 日志。此后提交的 op 一定走订阅到达，此前的一定在补发里，不重不漏（`hello` 原来就是为同样的理由在锁内订阅并读修订）。
2. **凡是答 op 的错误都带 `op_id`**：权限拒绝、`CLAIM_HELD`、`STALE_BASE_REVISION`、`OP_SUPERSEDED`、`OBJECT_DELETED`、`OBJECT_REFERENCED`、提交失败。
3. **带结构的 op 全有或全无**：一个 op 里只要有一条不是字段修改（新建、删除、拓扑类），其中任何一条被拒，整个 op 都不生效，每条错误都是 `rejected: true`。只有字段修改的 op 照旧逐条判（§3.3 的「不同字段自动合并」不变）：让位的那几条各有一条不带 `rejected` 的错误，其余的生效；全部让位时是 `rejected: true`。并列进冲突条目的两条照旧「两边都不生效、其余的照样提交」。
4. 持久化不变：补发读的就是现有的 `ops` 表。

### 2.4 客户端：发件队列

本会话的每个 op 进一条队列（`collab::State::outbox`），**一次只有一个在途**：队首发出去，等到它的答复再发下一个。答复是下面四种之一：

| 答复 | 处理 |
|---|---|
| 带着它的 `op_id` 的 `op_applied` | 出队；基线前进（照旧不再应用到图上，只处理服务器改派的位号） |
| 带着它的 `op_id`、`rejected: true` 的 `error` | 出队；**撤回那一步**（§2.5） |
| `op_ids` 里有它的 `conflict` | 出队；不撤回（并列的一方本地的值保留到裁决，现有做法） |
| 不带 `op_id` 的、属于拒绝 op 的 `error`（旧服务器） | 出队；不撤回（旧行为） |

带 `op_id`、不带 `rejected` 的 `error` 只是知会（它的 `op_applied` 随后就到）。

为什么一次一个：被拒的那一步要撤回，而撤销栈只能从顶上往下撤。一次一个在途，就保证「那一步之后本地又做的几步」都还没发出去——它们随那一步一起悄悄撤回、进重做栈，房间从没见过它们，不需要再广播什么；用户可以重做，重做是新的 op。若允许多个在途，后面的 op 可能已经生效，撤回它们就得再发反向的 op，次序与基线都说不清。代价是每一步要等上一步的答复（局域网上几十毫秒）。

每个队列项记着：`op_id`、载荷、**做这一步时的基线**（发的时候取它与当前基线中较小的那个：房间往前走了就用旧基线，让服务器照三段规则判落后；服务器换了库、修订变小了就用新的）、它对应哪几个撤销步（撤销步上新加一个编号 `collab_step`）以及它是「做上去」还是「撤下来」。

**离线**：会话断了（本次运行里有过会话）之后，本地的每一步照常进这条队列，只是不发；命令行说「已排队」。从没连上过的客户端不排队（照旧：第一次加入时把图当作房间的样子）。只读会话、已标成不一致的会话照旧不提交也不排队。

**重连**：`hello` 带 `since`（传输线程自己记着它交给界面的最后一个修订，所以不依赖界面线程处理断开事件的时机）。`welcome` 带 `replay_from` 时，客户端的基线留在原处，等补发的 `op_applied` 一条条到；到齐（基线等于 `welcome.base_revision`）之后再开始发队列。补发里若有本会话断线前已经发出、服务器其实已经提交的 op（按 `op_id` 认），它出队，不再发第二次——所以每个 op 恰好生效一次。`welcome` 不带 `replay_from` 而房间比自己新：照旧标成不一致（补不上），队列留着不发，状态里看得到。

**`SESSION_EXPIRED` / `SESSION_UNKNOWN`**：客户端收到就关掉这条连接、立刻走重连阶梯重新加入（新会话、带 `since`、补发、发队列）。在途的那个 op 没有被答复，重连后照上面的规则重发。

### 2.5 撤回被拒的一步

找到那个 op 对应的撤销步（按 `collab_step`）：

- 它是「做上去」的（新做的一步、或一次重做），还在撤销栈里：从栈顶**悄悄撤销**到它为止——不广播（房间没有它们）、不受只读与认领的拦截（这是在恢复房间的状态）、不打「Undo」的提示。撤销之后照现有机制把这一步之后别人的变更再写一遍（`replay_remote_after`），所以落后让位的字段最后是胜出的值，不是这一步之前的旧值。这几步进重做栈，用户可以重做。
- 它是「撤下来」的（一次撤销），还在重做栈里：悄悄重做回去。
- 它已经不在该在的栈里：若本地已经是房间的样子（做上去的一步已被用户自己撤销；撤下来的一步已被重做），什么都不用动；否则（重做栈被新的一步清掉了）没法恢复，标成不一致并说明。

被拒的 op 后面排着的项（一次一个在途，所以它们都还没发）按做的先后过一遍（`collab::Refused::account`），分成两类：

- **随它作废**：再动被拒那几步的（用户自己把它撤了、又重做了）；以及**在它上面做的**——被拒的那一步还在图上的时候新做的步骤、对它们的撤销与重做。房间没有被拒的那一步，这些项要么无从谈起，要么说出去会让对端收到「改一个它没有的对象」。它们对应的步骤若还在图上，随被拒的一步一起撤回。被拒的是一次撤销时对称：在它之后继续撤掉的更早的步骤随它一起恢复。
- **照发**：被拒的那一步已经不在图上之后做的（用户先把它撤了，再去做别的）——与它无关。

有一种情况撤不干净：排在后面的某一次撤销（或重做）把被拒的步骤和房间已有的步骤**一次**动了（`UNDO 3` 跨过了被拒的那一步）。那个 op 没法只说一半，整个说出去又等于让房间撤回它从没有的东西。这时不动图面，把会话标成不一致并说明（与「重做栈被清掉、找不到那一步」同样处理）。

命令行上是一条警告（不是命令失败：它不是当前正在跑的命令造成的，自动化把命令行的最后一条错误当作它刚执行的命令的结果），写明哪一步、错误码与服务器的说明、撤回还是恢复、连带了几步、作废了几个排队的 op。`/collab/status` 多出 `queued_ops`、`catching_up`、`rejections`（最近几次：`op_id`、`code`、步骤名、处理结果、动了几步、作废了几个 op），`last_error` 也是这句话。带 `op_id` 而不带 `rejected` 的错误（op 里的一条变更让位，其余的生效）照旧用原来的那句「服务器拒绝了请求（码：说明）」。

### 2.6 与认领、只读、冲突规则怎么相处

- 认领：客户端不知道的占用（占用的授予只告诉申请者）由服务器 `CLAIM_HELD` 拒绝，现在本地那一步会撤回。客户端知道的占用照旧在本地就拦下。离线排队的 op 重连后同样受占用检查——占用是按会话的，旧会话的占用在心跳超时后已经释放，别人可能占了。
- 只读：离线期间图纸被切成只读、或角色变了，重连后服务器在 `welcome` 后面跟一条 `readonly_downgrade`；队列里的 op 发出去会被拒（`rejected`），于是整串离线修改撤回并逐条说明。只读会话自己不会往队列里放东西（照旧在 `push_undo_entry` 撤回）。
- 冲突：离线修改带的是断线前的基线。别人在此期间改了同一个字段 → 落后让位（`OP_SUPERSEDED`，审计里有 `property_superseded`），本地撤回到胜出的值；改的是别的字段 → 合并；并列窗口只对同一基线、窗口内到达的两条成立，离线修改不会进冲突条目。契约 `VAL-CROSS-008` 的两种结局（提交为 op，或判为基线冲突并留痕）之外没有第三种：不会悄悄丢。

### 2.7 顺带的两件小事

- **认领的到期时间**：`welcome.claims[].expires_at` 原来在 `messages.rs` 被丢掉。现在留在客户端状态里（`claim_expiry`：位号 → 到期的 Unix 秒），被拒的申请带回来的到期时间也记进去，释放时清掉；`/collab/status` 多一个 `claim_expiry`。自己申请成功的占用服务器没有回到期时间（`claim_granted` 里没有），这一格是空的。
- **`SESSION_EXPIRED`**：见 §2.4，重新加入。

### 2.8 测试与端到端

- 客户端状态与应用层用例（过滤词 `collab_offline_queue`）：离线的几步排队、重连后按序发、一次一个在途；补发期间基线逐条前进、到齐才发；补发里认出自己的 op 不再发；被拒的一步撤回（栈顶的、上面还有几步的、已被自己撤销的）；落后让位撤回到胜出的值；不带 `op_id` 的旧式错误不撤回；`conflict` 放行队列；`SESSION_EXPIRED` 触发重连；到期时间留在状态里。
- 服务器用例：带 `since` 的 `hello` 补发且与加入不重不漏；错误带 `op_id`；带结构的 op 全有或全无；`conflict` 带 `op_ids`。
- 端到端 `y08_offline_reconcile.py`（`VAL-CROSS-008`）：杀掉服务器；u1、u2 各自离线改一处（不同字段）；重启服务器；两边 60 秒内重连（新会话）、两边的图一致、服务器侧读回两个值、审计里有两条。再做一轮同字段：后到的一方被拒、本地撤回到胜出的值、有提示、审计里有让位记录。再做一轮占用：u1 占着的位号 u2 不知情地去改，被 `CLAIM_HELD` 拒绝并撤回。

### 2.9 这一项不做的

- 队列只在内存里：离线期间退出程序，排队的修改留在保存的文件里但不会再提交。
- 已标成「不一致」的会话仍然只能取得最新图纸后重开；补发解决的是「断线期间错过」，不是「应用不上」。
- 并列的一方在裁决前本地保留自己的值（§17.6 之 4，等操作员定）。

### 2.10 实现记录（与上文不同或上文没写到的）

1. **op 是交给某一个会话的**（传输线程内部的事，不在线上）。界面线程知道断线比传输线程晚：传输线程已经在下一个会话上了，界面可能还把 op 交给它以为活着的上一个会话；等它处理到「断开」「已连接」两个事件，又会把同一个 op 再交一次——房间就会收到两遍。所以交给传输线程的每个 op 带着它是给哪个会话的（`Outbound::Op.session_id`），传输线程只发给当前会话的，别的丢掉并记一行日志；界面知道新会话之后会重新交来。
2. **自己在上一个会话里已提交的 op 之后的步骤，基线跟着走**。服务器按会话认「自己的修改不算落后」；重连后是新会话，断线前已被房间收下、答复却没到的那个 op，在服务器眼里成了别人的。排在它后面的步骤是在它之上做的，若仍带着旧基线去，同一字段会被自己前一步「胜出」。所以补发里认出自己的 op（修订 R）时，队列里基线恰好是 R−1 的项改成 R（它见过 R−1 为止的一切，R 是自己的）。基线更早的项不改：R 之前还有别人的修订它没见过，该让服务器照规则判。这种混合情形（同一个很窄的窗口里既丢了答复、又夹着别人的修订、后一步又改同一字段）下后一步会被判让位并撤回——安全、有提示，但不是用户想要的；要彻底就得让 `hello` 带上「我接着哪个会话」并由服务器把旧会话的修改记到新会话名下，没有做。
3. **发出去的基线记回队列项**：发的时候取「做这一步时的基线」与「房间当前修订」中较小的，并把它写回队列项，状态与测试读到的就是线上那个数。
4. **被拒时还开着的一步**：服务器的拒绝到达时若有一步还没收口（命令进行中），先把它收口（与别人的变更到达时一样），它排在被拒的一步之后，按 §2.5 的规则处理。
5. **只读降级的旧读法保留**：带 `op_id`、码是 `PERM_DENIED_STATE` 且带 `holder` 的错误，除了是那个 op 的答复，仍然先按原来的读法把会话降为只读。
6. **`SESSION_EXPIRED` 的落点**：`messages::read` 把它读成 `Frame::Rejoin`，传输线程关掉连接、按「断开」上报（原因里带着码），随后走重连阶梯；不再作为 `ServerError` 事件上报。
7. 测试替身：应用层用例里站在两个编辑器之间的「房间」用的是服务器自己的逐条判定（`DrawingModel`）加 §2.3 的整包规则；服务器对这条规则的遵守由服务器自己的用例管，端到端场景用真服务器。

## 3. CT-15 连接符跨图同步

### 3.1 现状

- `PIDCONNECTOR` 在命中的管线 / 信号线上放一个连接符（半径 3 的圆，`PID_AUTHOR` 的 `topology` 是 `connector_in` / `connector_out`，`type` 分管道与信号线），拓扑表 `connectors` 里记一条（种类、线号、对端）。同一线号同图第二个流入被拒（`DUPLICATE_INFLOW_CONNECTOR`），都在本地。
- 配对只在**同一个进程的两张图**之间：`PIDCONNECTOR <种类> <document_id>:<handle>` 或 `PIDPAIR`，两侧写 `peer`，并在配对那一刻把流出侧线体的字段（管道五个下传字段；信号线的 `起点仪表`、`终点仪表`）抄到流入侧线体。之后流出侧再改，流入侧不动。
- 协同里：连接符的新建不广播（同一张图的对端看不到它）；服务器认 `create_connector`（按「改这条管线的连接关系」判先后，原样记在 `connectors` 里），字段没有定义；房间按图分，服务器不在两张图之间转发任何东西。

### 3.2 做法

连接符的新建与删除像管线一样说给**本图的房间**；**配对由服务器做**——它是唯一同时看得见两张图的一方；配对之后，流出侧线体那几个字段的每一次生效的修改，由服务器在流入侧那张图的房间里再提交一次。客户端不需要打开对端那张图。

### 3.3 消息与字段

客户端 → 服务器（连接符所在那张图的会话里）：

```json
{ "kind": "create_connector", "line_tag": "L-1001", "connector": "pipe_out",
  "at": [120.0, 0.0], "target_drawing": "PID-1102",
  "line_props": { "管道等级": "A1A", "公称直径": "DN50" } }
{ "kind": "delete_connector", "line_tag": "L-1001", "connector": "pipe_out", "at": [120.0, 0.0] }
```

- `connector`：`pipe_in` / `pipe_out` / `signal_in` / `signal_out`。`at`：它在线上的位置。连接符没有位号，一张图里它就是「`line_tag` 上、`at` 处的那个 `connector`」。
- `target_drawing`：另一端在哪张图上，用服务器的图号。可以不带（流入的一端不必说自己从哪来）。
- `line_props`：所在线体当前的那几个要沿连接符传的字段（做这一步的人图上的值）。线体若是会话开始前就在文件里的，服务器从没听说过它的字段；有了这个，配对时才有值可传。服务器只拿它补自己没有值的字段，已经有值的（来自生效的 `set_property`）以自己的为准。
- `delete_connector`：连接符没了（删除，或撤销了新建）。

服务器 → 房间（服务器自己发起的 op，`op_id` 以 `pair-` 或 `carry-` 开头，照常占一个修订、进 `ops` 表与审计）：

```json
{ "type": "op_applied", "op_id": "pair-PID-1101-7", "revision": 4, "changes": [
  { "kind": "pair_connector", "line_tag": "L-1001", "connector": "pipe_in", "at": [20.0, 0.0],
    "peer_drawing": "PID-1101", "peer_line_tag": "L-1001", "peer_connector": "pipe_out" },
  { "kind": "set_property", "object_ref": "L-1001", "field": "管道等级", "value": "A1A" } ] }
{ "type": "op_applied", "op_id": "carry-PID-1101-9", "revision": 5, "changes": [
  { "kind": "set_property", "object_ref": "L-1001", "field": "管道等级", "value": "A1A" } ] }
```

- `pair_connector`：本图的哪个连接符配上了、对端是哪张图哪条线上的什么连接符。`peer_drawing` 为 `null` 表示对端没了，回到未配对。
- 流入侧那张图的配对 op 里，跟着流出侧线体当时的字段值（普通的 `set_property`，`object_ref` 是流入侧的线号）。
- `carry-…`：配对之后流出侧线体字段的修改，在流入侧房间里的那一份。

### 3.4 服务器的规则

1. **判定**：`create_connector` / `delete_connector` 照旧是「改 `line_tag` 的连接关系」（基线落后于别的会话对同一条线的改动 → `STALE_BASE_REVISION`；认领着这条线的会话之外的人 → `CLAIM_HELD`）。新增一条：同一张图同一线号上已经有同族的流入连接符，再来一个 → `DUPLICATE_INFLOW_CONNECTOR`，整个 op 不生效（两个人同时各建一个，本地都通过，后到的在这里被拒并在本地撤回——CT-14 的机制）。
2. **配对**（一个带 `create_connector` 的 op 在图 X 生效之后，在同一把锁里）：
   - 它是流出、带 `target_drawing = Y`：在 Y 里找同一线号、同族、还没配对、且没有另指来处（`target_drawing` 缺省或等于 X）的流入连接符。
   - 它是流入：在各张图里（它带了 `target_drawing` 就只在那一张里）找同一线号、同族、还没配对、`target_drawing` 指着本图的流出连接符；有多张图符合时取图号最小的。
   - 找到就配上：两边的模型各记对端；两边的房间各提交一个 `pair-…` op。流入侧的那个 op 带上流出侧线体当前的字段值。
3. **传递**（一个 op 在图 X 生效之后）：其中每条 `set_property`，若对象是 X 里某个**已配对的流出连接符**所在的线、字段属于那一族要传的字段，就在对端图 Y 的房间里提交一个 `carry-…` op 写同一个字段。Y 里那条线若还有已配对的流出连接符，接着往下传（按图记着走过的，环不会转第二圈）。
4. **解除**：`delete_connector` 删的是已配对的连接符 → 对端房间提交一个 `pair-…` op，`peer_drawing: null`。此后不再传。
5. 服务器发起的 op 的会话名是 `link:<起因所在的图>`，用户记起因那个 op 的用户；审计各记一条（`pair_connector`；`set_property`，说明里写「沿连接符自 X 的 T」）。它们不过占用与只读的检查——这是源图已经收下的修改的后果，不是对端图上谁的写入；流入侧那张图即使是只读，值也照到（否则两张图在这几个字段上不一致）。Y 里的人此后带着旧基线改同一个字段，照三段规则让位给它。
6. Y 的会话的基线随这些 op 前进（与本房间的 op 一样由广播带着走）。Y 没有人在线也照样提交：下次有人加入，按 `since` 补发。

持久化不变、协议版本不变：没有新表、新列；服务器发起的 op 就是 `ops` 表里的行，重启后重放日志得到同样的连接符与配对（`pair_connector` 只认会话名以 `link:` 开头的行，客户端发来的同名变更只是原样转发的不认识的变更）。新增一个只读查询（列出所有图号）。

### 3.5 客户端

- `PIDCONNECTOR <种类> [<对端>]`：第二个参数是 `<数字>:<句柄>` 时照旧是同进程配对；否则它是**目标图号**，记在连接符的拓扑记录里（`peer_drawing`），随 `create_connector` 说给服务器。
- 说：新建连接符的那一步 → `create_connector`（带 `line_props`）；连接符没了（删除、撤销新建）→ `delete_connector`。只是改了对端（本地 `PIDPAIR`）不说。
- 听 `create_connector`（同房间别人建的）：本图同一位置没有就建一个（圆、作者记录、拓扑记录），有了不动；找不到那条线 → 记为应用不上。听 `delete_connector`：删掉那一个。
- 听 `pair_connector`：在本图那个连接符上记下对端——拓扑记录的 `peer_drawing`、`upstream` / `downstream`，实体的 `connector_peer` 写成 `<对端图号>:<对端线号>/<对端种类>`（跨进程的对端没有句柄可言：同一个连接符在每个客户端的图里句柄各不相同；同进程两张图之间的 `<document_id>:<handle>` 不变）。`peer_drawing: null` → 清掉。
- 沿连接符来的字段是普通的 `set_property`：照现有路径写到线体上，线 → 管路 → 管段的下传链跟着走。
- 重复流入照旧在本地就拒（`DUPLICATE_INFLOW_CONNECTOR`，写入之前）。

### 3.6 次序与幂等

- 两张图各有自己的修订序列；配对 op 与传递 op 在各自房间里占各自的下一个修订，房间内的次序仍由那把锁保证。
- `create_connector` 说两遍（撤销后重做、补发）：客户端按（线号、种类、位置）认，已有就不再建；服务器的模型里同一个（线号、种类、位置）只留一条。重做之后服务器重新配对。
- 传递的是「值」，写两遍结果相同。

### 3.7 与认领、只读、冲突规则怎么相处

- 认领：占着线号的人之外，别人往这条线上建 / 删连接符被服务器拒（`CLAIM_HELD`），本地那一步撤回。沿连接符到达的值不受流入侧占用的拦截（§3.4 之 5）。
- 只读：只读会话建不了连接符（本地与服务器两处都拦，照旧）。只读的流入侧图纸仍然收到沿连接符来的值——**这一条是我定的，需要操作员知道**：另一种做法是拒收并让两张图不一致。
- 冲突：流入侧的人与沿连接符来的值改同一个字段，按普通的先后规则（后到且基线落后的让位）。并列窗口只对同一房间里两个会话的 op 成立，传递 op 不进并列窗口。

### 3.8 测试与端到端

- 服务器用例（名字带 `collab_connector_cross_drawing`）：流出在先 / 流入在先都配上，两个房间各有一个 op；配对时与配对后的字段到达对端房间并进对端的 `ops`；不属于那一族的字段不传；重复流入被拒；删掉一端后不再传；重启（重放日志）后配对还在、还能传。
- 客户端用例（同名过滤词）：建连接符的一步说成 `create_connector`（带目标图号与线体字段）；撤销说成 `delete_connector`；同房间的对端照着建出同样的连接符与拓扑记录；`pair_connector` 写到本图的连接符上；沿连接符来的字段经下传链到管路与管段；两个各开一张图的编辑器经「服务器」配对并传值（服务器这一侧用的是 `ocs_collab` 里的同一段配对代码）。
- 端到端 `y09_connector_cross_drawing.py`（`VAL-CROSS-009`）：u1 开 PID-1101、u2 开 PID-1102，各有管线 L-1001；u1 建流出（目标 PID-1102），u2 建流入；双方各收到 `op_applied`；u1 改 `管道等级` 为 A1A，u2 的 L-1001（以及它的管路、管段）读回 A1A；u2 再建第二个流入 → `ok=false`、`DUPLICATE_INFLOW_CONNECTOR`；两侧截图。

### 3.9 这一项不做的

- 连接符被移动（改位置）不同步；管线被删时它上面的连接符由客户端各自的清理规则处理，不另发消息。
- 流入侧往回传（下游改了不影响上游）；一个流出对多个流入。
- 对端图号写错（没有这张图、那张图上没有同线号的流入）：就是一直不配对，不报错——之后那边建了流入会配上。
- 界面上的跳转（点连接符打开对端图）。

### 3.10 实现记录（与上文不同或上文没写到的）

1. **配对与传递的规则在协议 crate 里**（`ocs_collab::link`）：纯函数 `follow`，经 `Rooms` 这个接口够到「保管图纸的一方」。服务器实现它（模型表、库、房间广播，都在提交那把锁里）；测试用内存里的替身实现它——协议 crate 自己的用例、客户端「两个各开一张图的编辑器」的用例用的都是这同一段代码。
2. 服务器发起的 op 的 `op_id`：`pair-<起因图>-<起因修订>`（一个 op 里第二条以后的变更再加 `-<第几条>`）、`carry-<来源图>-<来源修订>`。
3. 重复流入的判定在 `DrawingModel::judge`（`Verdict::DuplicateInflow`），错误码常量 `DUPLICATE_INFLOW_CONNECTOR` 进 `protocol::codes`（与编辑器本地用的是同一个字面量）。同一个连接符说第二遍（重做）不算重复。
4. **客户端找连接符按实体找**（种类、位置、它脚下的线），不靠拓扑表：本地撤销一步带结构变化的操作会把拓扑表还原到那一步之前，别人后来建的连接符的记录跟着没了，实体还在。所以「它在不在」看实体，找到了就把记录补回去；撤销 / 重做之后别人关于连接符的说法按原次序再对齐一遍（`replay_remote_after`）。
5. 解除配对时流入侧记录里的 `peer_drawing` 不清——分不出它是这个连接符自己说的来处还是配对时写上的；`downstream` 与实体的 `connector_peer` 清掉。
6. 并列窗口（`--tie-window-ms`）里的 op 到期提交后同样跟着配对与传递。**没有接上的两条提交路径**：裁决（`/conflicts/{id}/resolve`）写下的字段值、以及并列的 op 里没有并列的那部分变更——这两处生效的线体字段不会沿连接符传。
7. 管线整条删除时，服务器模型里它上面的连接符留着（可能还记着对端），不再有东西沿它传（线体的字段没人写了），但对端不会被告知解除。§3.9 已列为不做。
8. `PIDCONNECTOR` 的第二个参数按有没有冒号分两种读法（§3.5）；带冒号而不是 `<数字>:<句柄>` 的照旧报 `CONNECTOR_PEER_INVALID`（2026-11-08 的裁决不变）。信号线连接符下传的两个字段改为取协议 crate 里的同一份清单；管道的五个字段有一条用例盯着两边一致。
9. 既有测试的改动只有一处机械的：CT-14 的测试替身里对 `Verdict` 的 `match` 多认一个新变体。
