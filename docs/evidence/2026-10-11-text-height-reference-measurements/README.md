# 参考图上的文字字高：没有被放大 1.67 倍（2026-10-11，U6）

> 任务 t-326（协同组 pid），计划 `docs/plans/2026-10-11-dash-pitch-follows-a-view-scale.md` 的文字侧补充。U1 量的是虚线节距和线宽，本文只量字高。
> 只读产出：没改 `src/`、golden、测试、计划文件；没跑 cargo（当时已有别的会话在编译）。
> 执行者：grok-4.7-26。

## 1. 结论（一句）

**文字不是 1.67。** 拉丁大写按「A 的顶 = 文件字高」去比，干净样本的比例是 **0.92–1.00**（±0.5 px，约 ±0.08 到 ±0.10）。1.67 会让 2.469 mm 的字落到 8.2 px，这些字的墨只占 5–6 个像素行。宋体汉字相对 OCS 的 em 框是 1.29–1.54，相对「A 的顶 = 字高」是 0.90–1.08，两条都不是 1.67。

所以 U1 的虚线比例 **不是**「全部 style 尺寸统一放大」。`style.dll` 里那个会乘字高的 `+24`（以及单位因子）如果就是虚线上的 1.67，参考图上的字高也该是 1.67。不是。

## 3. 字体的 cap / em：怎么从比例里拿掉

OCS 对同一段文字按文件字面字高画，但「字面」对拉丁和汉字不是同一个框（`src/scene/text/ttf_glyph.rs` 的 `cap_height_units` / `em_scale`）：

- **拉丁**：字高 = 大写 **A 的外形顶**（`yMax`），不是 OS/2 的 `sCapHeight`，也不是 em。本机 Arial 与 Arial Narrow：upem 2048，A 的 `yMin = 0`、`yMax = 1466`，cap/em = **0.716**。大写墨高因此就等于字高。本文拉丁比例 = 量到的墨高 / 文件字高，**不再乘 0.716**。若有人拿 em 当字高，会把 1.0 读成 0.72。
- 数字 `0` / `6` 比 A 略高：`yMin = −25`、`yMax = 1472`，墨高 / A 顶 = **1.021**。管线号整段的顶是大写、底可能落到数字下沿，这 2% 在 2.469 mm 上只有 0.05 mm = 0.10 px，小于 ±0.5 px，表里不另乘。
- **宋体拉丁**（表内 `A3-06D01`）：A 的 `yMin = 4`、`yMax = 179`（upem 256，`sCapHeight = 175`）。墨高 / A 顶 = 175/179 = **0.978**。表里用这个因子。
- **宋体汉字**：OCS 把 **em 框** 缩成字高，不把 A 的顶缩成字高。`说` 的墨高 / em = 235/256 = 0.918，墨高 / A 顶 = 235/179 = 1.313。两种预期都给出，避免把 cap/em 误当成 view-scale。

`说` 若按 em 框再乘 1.67：0.918 × 6.350 × 1.67 = 9.73 mm = 19.4 px，比实测 17.46 px 多 **2.0 px**，超出 ±0.5 px。表头若按 em 框乘 1.67 大约是 9.4 px，实测 7.46 px。两条都排除「汉字也被乘了 1.67」。

## 5. 对计划 §3 的含义

- **P-D1**：虚线周期是 1.67（U1），字高不是。单一比例如果乘的是「每一个 style 尺寸」（虚线、线宽、点标记、字高），字高应当同样是 1.67。参考图否定了这一条。1.67 更像只进入虚线 / 点标记那条消费路径，而不是整张图的 view-scale。字高在 `style.dll` 里即便也会被 `+24` 和单位因子乘，**这个参考图上乘出来的不是 1.67**——要么文字这条路径上的因子是 1，要么虚线上的 1.67 根本不是那个共享因子。来源仍等 U2 / U3。
- **P-D2**：文字不支持「线宽和虚线用同一个 1.67」。U1 里只有 0.70 mm 的线粗得过栅格下限，而且和 1.67 只是相容。文字这个同样来自 style 的尺寸清楚地落在 1.0 附近，没有跟着虚线走。
