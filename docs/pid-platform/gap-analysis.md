# OpenCADStudio 现状差距与复用映射

本文档对 OpenCADStudio 现有能力与目标智能 P&ID 平台做差距分析与复用映射，回答三个问题：哪些现有能力可以直接复用，哪些需要在现有实现之上扩展后承担新职责，哪些必须从零建设。每一项能力被指派唯一的处置结论：复用、改造或新增，全文不再给出第四种结论。

文中所有关于现状的断言都以仓库内可核验的路径为依据：处置为复用或改造的行在证据路径列给出文件或目录，处置为新增的行以 — 标记。凡是没有路径支撑的说法不进入本文档，使差距分析可追溯、可复核，也避免把尚未实现的能力误述为现状。

## 核验方法与处置口径

- 复用 = 直接调用现有实现，不改变其公开行为与数据结构；
- 改造 = 以现有实现为主体，扩展字段、接口或界面后承担新职责；
- 新增 = 当前仓库没有任何对应实现，需要在目标架构中从零建设。

处置为复用或改造的每一行都在证据路径列携带一个仓库内路径，这些路径在本文定稿之前逐一以 Test-Path 核验存在；路径一律相对于仓库根目录书写。证据路径列中的 —（U+2014 em dash）表示该能力在当前仓库没有任何实现，对应处置必为新增。

已核验的量化事实：`src/io/pid_legend/` 共 12 个源文件、合计约 242 KB；`assets/pid-legend.json` 含 15 条块规则、6 条圆规则、11 个位号类与 50 个形状 id；MCP 面暴露 30 个读操作与 43 个执行操作。

## 已确认不存在的能力

下列十项能力已在仓库中逐一核查，确认没有任何对应实现；它们与能力矩阵中的十行新增一一对应。

### 位号主数据与带类型属性模型

当前仓库没有位号主数据，也没有带类型的属性 schema：位号只是字符串，散落在实体 XDATA 的 `label=`、GROUP description 的 `tagName=` 与识别结果的 `tag` 字段中；属性只有少量字符串键，没有类型、单位、默认值、必填标记与拼接规则。最接近的现有实现是 `src/io/pid_legend/xdata.rs`，它把 `class`、`label`、`lines`、`resolved` 四个键发布回实体，以及 `src/app/properties.rs`，它只编辑单个位号文本；两者都不校验唯一性、不携带类型、也不支持跨图纸查询。这一缺口使 L3 缺少权威数据源：位号唯一性、属性随图传递与 2D/3D 关联都缺少键级落点。处置为新增。

### 跨图纸拓扑持久化

识别与管道推断目前都是单图纸、一次性、在内存中完成：`Pipes` 结果每次重新计算、从不存储；页间连接符只被识别成一个符号类，不会转化为跨图纸的连边。最接近的现有实现是 `src/io/pid_pipes.rs`，它计算 run、tee 与线号族归并但只留在内存，以及 `src/io/pid_legend/xdata.rs`，它只把单图纸识别结果写回实体。这一缺口导致没有全项目管线清单、没有环路与悬空端检测、也无法按位号跨图查找。处置为新增。

### 可配置校验引擎

仓库中没有规则模型、规则 DSL、严重级别，也没有豁免与签核机制；现有的检查只是在识别阶段把未命中项分进未知块、未命名形状、无主位号、范围标注、重复位号五个例外桶。最接近的现有实现是 `src/io/pid_legend/mod.rs` 的例外分桶与 `src/io/pid_legend/export.rs` 的例外 JSON，它们能展示结果，但规则本身不可配置。这一缺口使 L4 缺少核心组件，设计规则检查无法成为交付前的可执行关卡。处置为新增。

### P&ID 语义材料清单

没有按类型与属性聚合的材料清单：`COUNT` 族按块或区域计数，`DATAEXTRACTION` 把属性抽取到 TABLE / CSV / TXT；两者都不认识位号、管线号与规格，也没有跨图汇总与模板。最接近的现有实现是 `src/app/commands/count.rs` 与 `src/io/pid_legend/export.rs`，它们提供通用计数与私域导出，但不具备 P&ID 语义。这一缺口使材料清单只能手工编制，不能随图纸刷新，也无法与位号对齐。处置为新增。

### 服务端项目库

项目数据目前只存在于 DWG/DXF 文件；`--http` 只监听本机回环、单客户端、无持久化；仓库中没有数据库、对象存储或作业队列。最接近的现有实现是 `src/rest.rs` 的 REST 传输与 `src/mcp.rs` 的 MCP 服务，二者都只是本机接口而非项目级存储。这一缺口使 L3 没有权威存储，批量识别、检查与材料汇总只能逐文件触发，无法作为项目级能力运行。处置为新增。

### 多用户权限与审计

仓库中没有用户、角色与租户概念；只有只读打开与文件占用锁，没有项目级或 PBS 节点级的读、写、发布、签核授权。最接近的现有实现是 `src/io/edit_lock.rs` 的本机文件占用锁与 `--read-only` 打开，它们保护的是文件本身而不是权限边界。这一缺口使项目无法拆分到多人协作，发布与签核没有可归责的主体。处置为新增。

### 图例库可视化编辑器

没有在界面内维护符号库的手段：新增符号需要手工编辑 `assets/pid-legend.json`；未命名形状只给出形状 id 与坐标，维护闭环是「读报告、改 JSON」。最接近的现有实现是 `src/ui/window/pid_legend_list.rs` 的只读识别结果索引，以及作为唯一规则来源的 `assets/pid-legend.json`；前者不能编辑，后者面向文本而非界面。这一缺口使设计人员不能自行维护符号库，多套图例标准无法落地。处置为新增。

### 协同设计

没有并发编辑、位号级占用与变更广播；文件占用锁只保护同一文件的本机单编辑器，不解决多人同时工作。最接近的现有实现是 `src/io/edit_lock.rs`，它提供的是同一台机器上对同一文件的编辑保护。这一缺口使多人无法同时编辑同一项目，冲突只能在文件级别被整体拒绝，无法细化到位号级。处置为新增。

### 审计日志

没有不可变审计日志；只有命令行历史与容量有限的事件环，随会话消失，不可查询、不可按对象追溯。最接近的现有实现是 `src/app/history.rs` 的快照撤销历史（默认 256 条 / 512 MiB）与会话内事件流：前者保存图形状态快照而非操作记录，后者既无持久化也无对象级索引。这一缺口使「谁在何时把哪个位号的哪个属性从 A 改成 B」无法回答，交付审计与合规要求不成立。处置为新增。

### 数据交换标准（DEXPI/ISO 15926/CFIHOS）

仓库中没有任何行业交换格式的读写器；输出只有私域 JSON/CSV 与带 `tagName` 的 SVG。最接近的现有实现是 `src/io/pid_legend/export.rs` 的私域 JSON/CSV 导出与 `src/io/plot_emit.rs` 的 SVG 位号分组，二者都不是 DEXPI、ISO 15926 或 CFIHOS 的映射。这一缺口使数据无法与业主、施工或运营系统交换，DEXPI 类交付要求无法满足。处置为新增。

## 复用结论

图纸侧链路（识别 → 结构化 JSON/CSV → 人工组合 → DWG/SVG 往返）已经跑通，可直接复用；数据侧链路（位号主数据 → 规则检查 → 材料清单 → 项目库 → 权限与审计 → 发布）目前是空的，必须在目标架构中从零建设。复用应首先锚定 `src/io/pid_legend/` 的识别结果与 `src/io/pid_legend/pairing.rs` 的配对算法，因为它们是把几何候选升级为「类型 + 属性集」对象的唯一入口；其次锚定 `src/app/commands/mod.rs` 的命令分发链与 `src/mcp.rs` 的自动化面，让新增与改造能力共用统一的调用通道。
